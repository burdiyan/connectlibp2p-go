# connectlibp2p-go

`connectlibp2p` implements Connect-Go v2's `Transport`, `ClientStream`, and `ServerStream` contracts. A call opens **one
new libp2p stream**, while libp2p retains the underlying authenticated peer connection. There is no RPC channel cache,
HTTP tunneling, second multiplexer, or application-level credit protocol.

This is an independently versioned transport, **not the Connect HTTP wire protocol**. The same generated client, service
implementation, and Connect interceptors work with this transport and `connecthttp`. Consumers need only the Go module;
no code-generation tools or grpc-go are required. Application services and codecs are not generated by this module.

## Install

Requires **Go 1.26 or newer**. Direct dependencies are pinned to Connect-Go **v2.0.0** and libp2p **v0.50.0**.
The public package is named `connectlibp2p`, despite the repository's `-go` suffix:

```go
import "github.com/burdiyan/connectlibp2p-go"
```

Install the module:

```sh
go get github.com/burdiyan/connectlibp2p-go
```

## Usage and supported contract

Register your generated service on a Connect dispatcher, then supply the libp2p transport to the generated client:

```go
rpcID := protocol.ID("/myapp/rpc/connectlibp2p/1.0.0")
server := connect.NewServer(serverInterceptors...)
yourserviceconnect.RegisterYourServiceHandler(server, implementation)
stop := connectlibp2p.Serve(ctx, localHost, rpcID, server)
defer stop()

client := yourserviceconnect.NewYourServiceClient(connect.NewClient(
    connectlibp2p.NewTransport(localHost, remotePeerID, rpcID),
    clientInterceptors...,
))
```

Replace `yourserviceconnect` with the package generated for your service by Connect-Go v2. The caller supplies libp2p
hosts and peer discovery/dialing policy; the transport does not create hosts. A complete runnable example with an
[`EchoService` schema](examples/echo/echo.proto), generated protobuf messages and Connect client/handler bindings,
and a service implementation is in [`examples/echo`](examples/echo/main.go):

```sh
go run ./examples/echo
# hello libp2p
```

Import `protocol` from `github.com/libp2p/go-libp2p/core/protocol`. Both setup functions require an explicit, nonempty
ID; there is no default or fallback. Empty IDs panic at setup. Register methods before serving; do not mutate the
dispatcher during calls. Each ID has one registration owner on a host: libp2p replaces an existing handler when the same
ID is registered, and stopping either owner removes that ID. Different IDs can serve independent dispatchers on the same
host. Expose only peer-safe methods; authentication of a libp2p connection is not authorization to access local APIs.

- Unary, server streaming, client streaming, and simultaneous bidirectional streaming.
- Lazy/eager request and response headers, ordered repeated values, base64 binary metadata, response trailers, and
  Connect client/server/per-message interceptors.
- Every RPC status code, opaque protobuf `Any` details, remote-error marking, and error scrubbing consistent with
  Connect HTTP. Local Connect errors retain their public code/message/details; forwarded remote errors become bare
  `Internal`; uncoded errors become bare `Unknown`; context errors retain their cancellation code. Causes and remote
  flags are never serialized. Panics become `Internal`.
- Deadlines, explicit abandonment with `Close`, automatic release on terminal status, idempotent
  headers/half-close/close, and shutdown that joins handlers and reader pumps.
- `CallInfo` carries the method spec, protocol `connectlibp2p`, protobuf codec, identity compression, per-message
  payload statistics, and the authenticated remote `peer.ID` in `TransportInfo`. Request headers cannot spoof this
  identity.
- One send-side operation and one receive-side operation may run concurrently. Multiple sends or multiple receives on
  the same stream are not supported, matching Connect's contract. Handlers must join their own goroutines before
  returning.

V1 intentionally supports **protobuf application messages and identity compression**. Custom codecs, JSON payloads,
compression negotiation, HTTP status codes, HTTP GET caching, CORS, and HTTP-specific transport options are not part of
this wire protocol. They are not requirements of the transport-independent Connect stream interfaces. Adding
codecs/compression later requires an explicit wire extension, not silent interpretation of ordinary metadata. Secure
transport and transport flow control come from libp2p; authorization, tracing, and application policy belong in
interceptors.

## Wire contract

Applications choose their own libp2p protocol ID and associate it with this **v1 framing contract**, for example
`/myapp/rpc/connectlibp2p/1.0.0`. The ID is used for libp2p negotiation/routing, not embedded in RPC frames. Both endpoints
must agree on the ID and the application/framing contract; matching IDs do not validate compatibility or authorize a
caller. There is no automatic version negotiation. Wire-incompatible revisions require a new protocol ID; ordinary
library updates need not change it. The module's release version and wire-protocol version are separate.

Every frame is a **one-byte kind + four-byte unsigned big-endian payload length + payload**. Length applies to one
message/control frame, never to the entire RPC. An encoder buffers at most one bounded protobuf message before sending
it; a response stream has no aggregate length or message-count limit.

| Kind         | Direction                   | Payload                                                                              |
| ------------ | --------------------------- | ------------------------------------------------------------------------------------ |
| 0 OPEN       | Client → server, once first | Protobuf `Open`: procedure, metadata, remaining timeout in nanoseconds               |
| 1 MESSAGE    | Either direction            | One protobuf application message, including zero-byte messages                       |
| 2 HALF_CLOSE | Client → server, once last  | Zero bytes; no more request frames are legal                                         |
| 3 HEADERS    | Server → client, once first | Protobuf `Metadata`, including empty metadata                                        |
| 4 END        | Server → client, once last  | Protobuf `End`: present `google.rpc.Status`, optional trailers; code 0 means success |

Control schemas are in `proto/connectlibp2p/v1/transport.proto`. Generated wire types are internal, not a public Go API.
Metadata uses a protobuf map with a repeated string value list for each key. Receivers canonicalize MIME keys, reject
duplicate case aliases and invalid keys/values/base64, and preserve value order. Code generation uses Buf with local
Go and Connect plugins; it is only needed when editing schemas, not when using the package or running the example.

The server derives cardinality from the registered method's `Spec.StreamType`, never from the client.
Unary/server-streaming methods require exactly one request; client/bidirectional-streaming methods accept zero or more.
Successful unary/client-streaming methods require exactly one response; server/bidirectional streams accept zero or
more. Missing or malformed terminal status is never success. A single-response client reads through END before
returning, so a late error is not lost.

## Cancellation, backpressure, and cleanup

HALF_CLOSE is **logical**, not `Stream.CloseWrite`: keeping the physical request direction open lets a server's reader
observe resets after the last request while the handler computes or sends responses. A normal client closes the physical
stream after reading END. An abandoned client resets it through context cancellation/Close.

Each server call has one unbuffered reader pump. That preserves bounded backpressure, but libp2p does not expose stream
cancellation independently of I/O: if the pump is blocked delivering an unread message to the handler, it cannot observe
a subsequent remote reset until consumption resumes. **This is not HTTP/2-equivalent cancellation.** No finite queue
removes the general problem; there is no credit protocol or dependency fork here. The propagated deadline and
server-owned maximum duration provide the backstop. CPU/database work must honor context, and streaming handlers must
keep receiving or return rather than wait forever for unrelated work.

Administrative cancellation/deadlines reset streams independently of protocol errors. Protocol cancellation interrupts
pending handler writes with a write deadline; the callback is joined before restoring the finalization deadline. Failed
partial writes are not followed by further frames: the RPC is aborted, not reported as success.

After writing END, the server closes its response direction and drains outstanding requests within a finalization
budget. This allows early interceptor rejection to reach generated unary clients, which finish sending before reading,
especially on QUIC. The server does not reset a completed reader and risk discarding queued status.

## Resource policy

- 8 MiB per application message, 64 KiB per control frame, checked before allocation.
- Frame kind/order and half-close length are also checked before payload allocation.
- Frame read/write buffers are admitted against libp2p's resource manager under the `connectlibp2p` service. Both
  directions share a conservative peak-live-buffer reservation, held until the stream closes/resets. Overlapping buffers
  count together; exceeding the peak requires a fresh admission check. This avoids per-message resource-trace allocation
  churn without disabling resource limits. A long-lived call retains its peak quota even after those buffers are freed.
  Decoded protobuf objects and memory retained by handlers remain the application's responsibility.
- Default maximum per `Serve` instance: 64 active incoming calls, 16 per authenticated peer; admission and finalization
  count as active. Overload resets without dispatching. Multiple dispatchers have independent admission limits.
- Initial OPEN budget: 5 seconds. Maximum call duration: 5 minutes. Combined terminal write/drain budget: 5 seconds. A
  shorter caller or parent deadline always wins.
- Override defaults by passing one `ServerOptions` value to `Serve`. Zero fields select defaults; negative values panic
  at setup. Limits cannot be disabled. Long-lived streaming services must explicitly select an appropriate duration.
- Configure libp2p's system/service/protocol/peer memory and stream limits for the deployment. The transport does not
  replace libp2p's connection admission/rate policy. Protocol scopes use the application-supplied ID; the
  `connectlibp2p` service scope is shared across this library's dispatchers.
- `stop()` is idempotent and synchronous. It cannot forcibly terminate Go handlers that ignore context; neither can the
  other RPC frameworks.

## Development and validation

Real TCP and QUIC peers exercise metadata, interceptors, all statuses, opaque details, all four shapes, concurrent
duplex calls, malformed requests, cardinality, exact message limits, cancellation after half-close, early rejection,
slow admission, blocked writes, bounded finalization, shutdown after protocol failure, and admission capacity recovery.
Regression payloads are generated from a small local test-only schema; no application checkout or workspace replacements
are needed. These adapter tests are not a completed security audit or proof of a particular deployment's authorization,
relay behavior, or resource policy.

```sh
mise install
mise run test
mise run vet
mise run lint
mise exec -- go run ./examples/echo
mise run generate # after editing .proto files
```

`mise.toml` pins Go, Buf, and golangci-lint and defines the development tasks. `buf.yaml` defines the local schema modules;
`buf.gen.yaml` runs `protoc-gen-go` and `protoc-gen-connect-go` locally at the runtime versions pinned in `go.mod`.
Buf compiles the schemas itself, so no `protoc` installation or remote generation plugins are needed.
The Google API schema dependency is pinned in `buf.lock`, not vendored. A fresh checkout needs network access to fetch
Go modules and Buf schema dependencies; subsequent generation can use their local caches.
Generated Go files are checked in. CI tests Go 1.26.0 and 1.27.1, checks formatting, and verifies reproducible generation.
Go-module users need neither Buf nor mise. Contributor guidance for coding agents is in [`AGENTS.md`](AGENTS.md).
